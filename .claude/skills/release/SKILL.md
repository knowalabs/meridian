# Release

## When to use

Use when the user asks to cut a release, publish a new version, or "ship" pending changes to npm. This workflow is destructive/hard-to-reverse at its last two steps (tagging, publishing) and must stop for explicit approval before each — never run it end-to-end unattended.

## Before you start

- CHANGELOG.md — the real format: a `## X.Y.Z` heading, then `### Patch Changes`/`### Minor Changes` with specific, why-focused bullets (see the `0.1.1` entry).
- Any pending files under `.changeset/` — what's queued for the next release.
- `.github/workflows/ci.yml`'s `publish` job — the only path that actually runs `npm publish`.
- `package.json`'s `version` field and `prepublishOnly` script.

## Steps

1. Read CHANGELOG.md's latest entry and list what's pending under `.changeset/`. Summarize what this release would contain and stop if nothing is queued.
2. Run `npx changeset version` — it consumes the pending changeset files into a new CHANGELOG.md entry and bumps `package.json`'s version. Do not hand-edit either file; this is the only sanctioned way `CHANGELOG.md` and the version move together.
3. **Stop and show the user** the resulting CHANGELOG.md diff and the new version number. Get explicit approval before anything is committed.
4. Once approved, commit the version bump using the `commit` skill's own approval flow (summarize, scan, propose the message, wait for approval) — do not fold this into an unrelated commit.
5. **Stop and show the user** the exact tag you're about to create (`v` + the new `package.json` version — `.github/workflows/ci.yml`'s publish job verifies this match and fails the release if it doesn't). Only after explicit approval, run `git tag` and ask again before `git push --tags`. Never force-push, never skip either approval.
6. Do not run `npm publish` yourself. Once the tag is pushed, CI's `publish` job runs `npm ci`, `npm run build` (via `prepublishOnly`), `npm test`, and `npm publish --provenance` using a secret (`NODE_AUTH_TOKEN`) and an OIDC context this session does not have. Watch the Actions run for that tag instead.

## Verification

- Before tagging, run the same chain CI runs: `npm run lint` → `npx prettier --check .` → `npm run build` → `npm run test:coverage` → `npm run test:e2e`. A failure here fails on all three CI OSes; fix it before tagging, not after.
- After pushing the tag, check the `publish` job's run in GitHub Actions succeeded — that is the only confirmation the release actually shipped.

## Done when

- [ ] CHANGELOG.md has a new entry generated by `npx changeset version`, not hand-written.
- [ ] `package.json`'s version matches the pushed tag exactly (`v<version>`).
- [ ] The user explicitly approved both the version-bump commit and the tag/push.
- [ ] CI's `publish` job for that tag succeeded.

## Never

- Never run `npm publish` locally — it bypasses provenance and the tag-matches-version guard `ci.yml` enforces.
- Never tag or push a tag without a separate, explicit approval from the commit approval.
- Never hand-edit CHANGELOG.md's version heading or `package.json`'s `version` outside `npx changeset version`.
- Never force-push or skip a hook to push a release through.

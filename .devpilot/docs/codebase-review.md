# Codebase Review — @sonalsithara/devpilot

## What this project is

DevPilot is a CLI tool (published as `@sonalsithara/devpilot`, invoked as `devpilot`) whose purpose is to make **any codebase AI-assistant-ready with one command**. In the project's own words (`README.md`): "One command to set up every AI coding tool on any machine." It handles four related jobs:

1. **Tool management** — detect, install and configure AI coding assistants (Claude Code, Codex CLI, Gemini CLI, Cursor, Copilot) via `devpilot doctor`/`install`/`uninstall`.
2. **Secret management** — store provider API keys in the OS-native secret store (macOS Keychain, Linux Secret Service, Windows DPAPI-wrapped file, or an encrypted-file fallback) via `devpilot auth`/`keys`.
3. **AI-kit generation** — the flagship feature, `devpilot generate`: scan a target codebase, build a "digest," have an AI provider (or a static fallback) write a codebase review and then generate rules, Claude subagents/skills/commands, prompts and docs, mirrored into every tool's own config format.
4. **AI routing** — `devpilot ask`/`router` picks the best-suited provider by cost/speed/quality/context size and can call either hosted APIs (Anthropic, OpenAI, etc.) or keyless local CLIs (Claude Code, Codex CLI, Gemini CLI, Ollama).

Domain vocabulary: "provider" (an AI backend, `src/providers/router.ts`), "vault" (secret storage, `src/core/vault.ts`), "digest" (the codebase summary fed to AI, `src/generate/digest.ts`), "artifact kind" (a category of generated file — rules/agents/skills/commands/prompts/docs, `src/generate/artifacts.ts`), and "kit" (the full generated output set).

## Architecture

- **`src/index.ts`** — process entry point. Imports `./core/colorflag.js` _first_ (deliberately, per its own comment) so `--no-color`/`NO_COLOR` is set before `picocolors` is loaded anywhere else. Registers `uncaughtException`/`unhandledRejection`/`SIGINT` handlers that funnel into `renderError`, checks the Node major version (≥18 required), and dispatches to either the interactive launcher (`runInteractive`, TTY-only) or Commander's CLI parser (`buildCli().parseAsync`).
- **`src/cli.ts`** — builds the Commander (`commander` v12) program: registers every subcommand (`doctor`, `install`/`uninstall`, `auth`, `keys …`, `generate`, `mcp …`, `ask`, `router`, `update`, `login`) and attaches global flags (`--verbose`, `-q/--quiet`, `--json`, `--no-color`) recursively to every command via `addGlobalFlags`. Actions call `done(exitCode)` (setting `process.exitCode`) instead of `process.exit()` so the interactive launcher can invoke commands in-process without killing the process.
- **`src/launcher.ts`** — the interactive TUI shown when `devpilot` runs with no args in a TTY (`showBanner`, `menuPrompt`, `runInteractive`). Renders a raw-mode arrow-key menu (`MENU: MenuItem[]`) with type-to-filter and free-text command fallback, using raw ANSI cursor control via `node:readline`.
- **`src/commands/*`** — one file per command group (`doctor.ts`, `install.ts`, `auth.ts`, `generate.ts`, `mcp.ts`, `ask.ts`, `update.ts`), each exporting the action functions wired up in `cli.ts`. This is the CLI-facing layer; it should stay thin and delegate real logic to `core`/`generate`/`providers`/`scan`.
- **`src/core/`** — cross-cutting infrastructure: `colorflag.ts` (color flag pre-processing), `errors.ts` (`CliError`, `renderError`, `EXIT` codes), `logger.ts` (`configureLogger`, `log`), `config.ts` (`loadConfig`/`saveConfig`, e.g. `router.models`), `vault.ts` (multi-backend secret storage — `KeychainVault`, `SecretToolVault`, DPAPI/encrypted-file backends, plus a non-secret `index.json` account-name index since neither `security` nor `secret-tool` can enumerate items), `fsx.ts` (`writeFileAtomic`, `backupFile`), `paths.ts` (`devpilotHome`, `ensureHome`), `exec.ts` (`run`/`runAsync`/`which` — shell-out helpers), `spinner.ts`, `pkg.ts` (`VERSION`).
- **`src/scan/`** — static analysis of the _target_ project. `analyzer.ts` exposes `analyzeProject(root): ProjectAnalysis` (languages, frameworks, scripts, dependency list, directory tree) and renderers `renderContextMarkdown`/`renderArchitectureMarkdown`.
- **`src/generate/`** — the AI-kit pipeline. `digest.ts` (`buildDigest`) turns a `ProjectAnalysis` plus source excerpts into the big prompt-ready text block (the "PROJECT DIGEST" seen at the top of prompts). `artifacts.ts` defines `ARTIFACT_KINDS` (rules, agents, skills, commands, prompts, docs), each with a `prompt(digest)` builder, a `fallback(analysis)` static generator, and `allowedPaths` used for path-safety validation (`isAllowedPath`) plus the `<<<FILE path>>> … <<<END>>>` block protocol (`parseFileBlocks`). `pipeline.ts` (`runGenerate`) orchestrates: pick a provider (`pickProvider`), get the AI to write the codebase review, then run each artifact kind's `prompt`/`fallback`, validate every returned path, and write via `writeFileAtomic`. Rules are also _propagated_ into every tool's own instruction file (`CLAUDE.md`, `AGENTS.md`, `GEMINI.md`, etc.) via `src/rules/generators.ts`.
- **`src/rules/`** — `generators.ts`: `generateRules`, responsible for mirroring `.devpilot/rules.md` into each tool's native config format.
- **`src/providers/router.ts`** — defines `PROVIDERS: ProviderSpec[]` (Anthropic, and keyless CLI-backed providers like `claude-code`, plus presumably OpenAI/Google/OpenRouter/Ollama per the README) with `cost`/`speed`/`quality`/`contextTokens` rankings, `route()` to auto-pick one, `modelFor()` to resolve config overrides, and a shared `post()` HTTP helper with timeout/retry/error-mapping (401→auth hint, 429→one retry then error, 404→model-not-found hint). CLI-backed providers shell out via `runAsync`/`which` (test-seamed by `setRunForTests`) instead of HTTP.
- **`src/mcp/`** and **`src/commands/mcp.ts`** — the MCP server marketplace (search/install/remove/list), installing servers into every detected tool's config at once (including Claude Desktop).
- **`src/plugins/`** — tool-specific install/config logic referenced by `devpilot install`/`doctor` (per `tests/plugins.test.ts`).

**Data flow for the flagship path (`devpilot generate`):** `commands/generate.ts` → `generate/pipeline.ts:runGenerate` → `scan/analyzer.ts:analyzeProject` (static facts) → `generate/digest.ts:buildDigest` (facts + source excerpts → text) → `providers/router.ts` (`pickProvider`/`route`, then `provider.ask(REVIEW_PROMPT + digest)`) → per-kind `artifacts.ts` prompts → `parseFileBlocks` → `isAllowedPath` validation → `core/fsx.ts:writeFileAtomic` → `rules/generators.ts` propagation into tool config files.

## Conventions & idioms

- **Strict TypeScript, ESM throughout.** `tsconfig.json` sets `strict`, `noUncheckedIndexedAccess`, `noImplicitOverride`, `noFallthroughCasesInSwitch`; `package.json` has `"type": "module"`, and imports use explicit `.js` extensions on relative paths even though source is `.ts` (NodeNext resolution) — e.g. `import './core/colorflag.js'` in `src/index.ts`.
- **`CliError` + `EXIT` codes for all user-facing failures**, not thrown raw errors — see `src/core/errors.ts`, and constructed with a `hint` field everywhere in `src/providers/router.ts`'s `post()` (e.g. `hint: 'Run "devpilot auth ${ctx.provider}" to update it.'`). Errors always carry actionable next-step hints.
- **Commands never call `process.exit()` directly** — they return exit codes and `cli.ts`'s `done()` wrapper sets `process.exitCode`, explicitly so the in-process interactive launcher (`src/launcher.ts`) can chain commands (comment in `src/cli.ts`: "Actions set process.exitCode instead of calling process.exit() so the interactive launcher can run commands in-process and keep going").
- **Atomic, permissioned file writes.** Secrets and generated files go through `writeFileAtomic` (`src/core/fsx.ts`) with explicit `mode: 0o600` for sensitive files (`src/core/vault.ts`'s `indexWrite`).
- **Test seams over mocking libraries.** Side-effecting singletons expose a `setXForTests(impl | null)` pattern: `setFetchForTests` and `setRunForTests` in `src/providers/router.ts`. Tests import these directly rather than using `vi.mock` on modules.
- **Path safety is explicit and tested.** `isAllowedPath` in `src/generate/artifacts.ts` blocks absolute paths, Windows drive letters, and `..` traversal before any AI-suggested file path is written — directly exercised in `tests/generate.test.ts`'s `isAllowedPath` describe block.
- **AI-response parsing is a defined text protocol**, not JSON: `<<<FILE path>>> … <<<END>>>` (`FORMAT_SPEC` in `src/generate/artifacts.ts`), parsed by a tolerant regex in `parseFileBlocks` that also unwraps stray markdown code fences models sometimes add.
- **Fail-closed AI generation, no silent template substitution.** In `generateKind` (`src/generate/pipeline.ts`), a failed AI call writes nothing for that kind (not a static fallback) so a later re-run can retry with AI — comment: "a failed kind writes nothing, so a later re-run regenerates it with AI."
- **Every artifact kind supports both AI and static generation** — `ArtifactKind.prompt()` and `ArtifactKind.fallback()` are required side-by-side (`src/generate/artifacts.ts`), enforced by the `static fallbacks` test in `tests/generate.test.ts` ("every kind produces at least one file inside its allowed paths").
- **Platform-conditional code is isolated per backend class**, not scattered with `if (platform === …)` — see `src/core/vault.ts`'s separate `KeychainVault`/`SecretToolVault`/`DpapiProtector`/`PlainProtector` classes implementing a common `Vault`/`KeyProtector` interface.
- **Secrets never touch argv when avoidable** — `KeychainVault.set` prefers `security -i` (stdin) "so the secret never appears in the process argument list," falling back to argv only if stdin mode fails; `SecretToolVault` always uses stdin.
- **Naming**: PascalCase for types/interfaces (`ProviderSpec`, `ArtifactKind`, `GenerateResult`), camelCase functions, `UPPER_SNAKE` for module-level constants (`PROVIDERS`, `ARTIFACT_KINDS`, `FORMAT_SPEC`, `DEFAULT_TIMEOUT_MS`).
- **ESLint config (`eslint.config.js`)** enforces `no-explicit-any`, `no-floating-promises`, `no-misused-promises` on `src/**` via `typescript-eslint`'s `recommendedTypeChecked`, but relaxes the unsafe-* family for `tests/**` since tests assert on parsed JSON constantly.

## Testing & verification

- **Framework:** Vitest (`vitest`, `@vitest/coverage-v8`).
- **Unit/integration tests** live in `tests/*.test.ts` (one file per module area: `analyzer`, `commands`, `config`, `errors`, `fsx`, `generate`, `launcher`, `mcp`, `platform`, `plugins`, `prompt`, `router`, `router-network`, `rules`, `update-ask`, `vault-backends`, `vault`), configured by `vitest.config.ts`: `include: ['tests/**/*.test.ts']`, excludes `tests/e2e/**`, coverage thresholds `lines: 70`, `branches: 60`, and explicitly excludes `src/launcher.ts` and `src/index.ts` from coverage ("exercised by humans and e2e smoke tests, not unit tests").
- **E2E tests** live in `tests/e2e/`, run via a separate config `vitest.e2e.config.ts` and require a build first (`pretest:e2e` runs `npm run build` before `test:e2e`).
- **Exact commands** (`package.json` scripts):
  - `npm run lint` → `eslint src tests`
  - `npx prettier --check .` (CI) / `npm run format` → `prettier --write .`
  - `npm run build` → `tsc -p tsconfig.build.json`
  - `npm test` / `npm run test` → `vitest run`
  - `npm run test:watch` → `vitest`
  - `npm run test:coverage` → `vitest run --coverage`
  - `npm run test:e2e` → builds first, then `vitest run --config vitest.e2e.config.ts`
- **CI (`.github/workflows/ci.yml`)** runs the full matrix — `ubuntu-latest`/`macos-latest`/`windows-latest` × Node `18`/`20`/`22` — executing, in order: `npm ci`, `npm run lint`, `npx prettier --check .`, `npm run build`, `npm run test:coverage`, `npm run test:e2e`. This ordering (lint → format-check → build → tests) is the de facto verification checklist for any change.
- **Test seams, not mocks:** network and subprocess calls are tested by swapping `setFetchForTests`/`setRunForTests` (see `tests/router-network.test.ts`), and fake timers (`vi.useFakeTimers()` + `vi.advanceTimersByTimeAsync`) drive retry/timeout logic (429 retry-then-fail, `AbortController` timeout) deterministically.
- **Isolation via temp dirs and env vars:** tests set `process.env.DEVPILOT_HOME` and `process.env.DEVPILOT_VAULT = 'file'` to sandbox the home directory and force the encrypted-file vault backend instead of touching the real OS keychain (`tests/generate.test.ts`, `tests/router-network.test.ts`).
- **Publish safety net:** the `publish` CI job verifies the git tag matches `package.json`'s version before `npm publish --provenance` (`.github/workflows/ci.yml`), and `prepublishOnly` runs `npm run build`.

## Gotchas

- **Import order matters in `src/index.ts`.** `./core/colorflag.js` must be imported _before_ anything that imports `picocolors`, because it mutates the `--no-color`/`NO_COLOR` environment state that `picocolors` reads at load time. Reordering imports here can silently break `--no-color`.
- **Commands must never call `process.exit()`.** They rely on `process.exitCode` via `cli.ts`'s `done()` so the interactive launcher (`src/launcher.ts`) can run multiple commands in-process in one session. Adding a raw `process.exit()` in a command would kill the interactive menu after one action.
- **AI kind generation is fail-closed, not fail-open.** If an AI call for one artifact kind fails, `generateKind` (`src/generate/pipeline.ts`) writes _nothing_ for that kind rather than silently substituting the static fallback — this is intentional so re-running `generate` retries with AI, but it means a single flaky provider call can leave a kind entirely unwritten on that run.
- **`--force` semantics:** by default `generate` skips any file that already exists (`skipped-exists` in `FileResult`); only `--force` overwrites. Don't assume re-running `generate` regenerates everything.
- **Path validation is mandatory for anything AI-suggested.** Any new artifact kind or AI-driven file write must go through `isAllowedPath` — it blocks absolute paths, Windows drive-letter paths, and `..` traversal, and is the only thing standing between a malformed/adversarial AI response and writing outside the project.
- **Windows vault backend uses PowerShell + DPAPI, not a native module.** `src/core/vault.ts`'s `DpapiProtector` shells out to `powershell -NoProfile -NonInteractive -Command …`, piping base64 over stdin — this is slow relative to native calls and fails hard if PowerShell isn't on PATH. Legacy stored keys without the `dpapi:` prefix are treated as plain hex for backward compatibility (`unprotect`'s fallback to `PlainProtector`).
- **Neither macOS Keychain nor Linux Secret Service can enumerate stored items reliably**, so `src/core/vault.ts` keeps a _parallel, non-secret_ index file (`keys/index.json` under `devpilotHome()`) of account names. Any direct manipulation of the OS vault outside DevPilot's `set`/`delete` methods will desync this index from reality.
- **Secrets avoid argv when possible** (`security -i` / `secret-tool` via stdin) but there's an argv fallback path in `KeychainVault.set` if stdin mode fails — that fallback does put the secret in `ps`-visible process arguments; be aware when touching that code.
- **CLI-backed providers (`claude-code`, presumably `codex-cli`/`gemini-cli`) use a sentinel model `'cli-default'`** (`CLI_DEFAULT_MODEL` in `src/providers/router.ts`) meaning "use whatever the signed-in CLI is configured with" — don't assume `modelFor()` always returns a real model string when working with these providers.
- **Long timeouts differ by provider type:** HTTP providers default to `DEFAULT_TIMEOUT_MS = 60_000`ms, but the `claude-code` CLI provider is given `timeoutMs: 600_000` (10 minutes) since it shells out to a full CLI session — don't reuse the HTTP default when adding new CLI-backed providers.
- **`.devpilot/` and `README_AI.md` in this repo's own working tree are untracked** (per current `git status`) — this is DevPilot's own dogfooded output from running `devpilot generate` on itself; don't treat them as hand-authored source when reviewing diffs.
- **Coverage thresholds exclude `src/launcher.ts` and `src/index.ts` on purpose** (`vitest.config.ts`) — don't flag low coverage there as a regression; they're meant to be covered by e2e/manual testing, not unit tests.
- **CI publish gating is tag-driven and strict:** the `publish` job only runs on `refs/tags/v*` push and hard-fails if the tag version doesn't match `package.json`'s version — bumping `package.json`'s version without tagging (or vice versa) will not publish, or will fail loudly if it does run.
